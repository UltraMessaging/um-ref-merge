# um-ref-merge — Merging a contributor's improved skill back upstream

## Scope

Use this skill when a **contributor** wants to merge their locally-improved
copy of the `um-ref` skill back into the upstream `um-ref` git repo. The
contributor is expected to be running Claude inside a git clone of the
upstream repo, with their active skill installed at
`~/.claude/skills/um-ref/` from some earlier release.

If the user is the **maintainer** doing a UM version upgrade of the skill,
this is the wrong tool — direct them to `um-ref/RELEASE_UPGRADE.md` in
their repo clone. This skill is about reconciling *contributor* changes,
not upstream releases.

## The problem

Between the contributor's install and the current upstream HEAD, both
parties have been editing the skill in parallel:

- The **maintainer** kept improving the skill and committed new versions.
- The **contributor** improved their local `~/.claude/skills/um-ref/`.

Neither side has git history of the other's edits. Combining them correctly
requires a **3-way merge** with three trees:

| Role   | Content                                            | Location                    |
| ------ | -------------------------------------------------- | --------------------------- |
| BASE   | The release the contributor originally installed   | Historical `um-ref.tgz`     |
| OURS   | Current upstream HEAD (maintainer's latest)        | Repo clone's `um-ref/`      |
| THEIRS | Contributor's improved local skill                 | `~/.claude/skills/um-ref/`  |

A "just copy their files over" approach loses the maintainer's changes;
a 2-way diff between BASE and THEIRS cannot distinguish "the contributor's
edits" from "changes the maintainer already made independently." A 3-way
merge anchored at BASE distinguishes them.

## Workflow

### Step 1 — Verify preconditions

- Current working directory is a clone of the upstream `um-ref` repo,
  with a clean `git status` (no uncommitted local edits — those would
  confuse the BASE identification in Step 2).
- **Do not `git pull` yet.** Step 2 uses the current HEAD vs.
  `origin/main` gap as its primary signal for identifying BASE; pulling
  first destroys that signal (though Step 2 has a reflog-based fallback
  for post-pull cases).
- The repo working tree contains at least `um-ref.tgz` and either a
  `um-ref/` directory or, for the earliest releases, only the tarball.
- The contributor's active skill exists at `~/.claude/skills/um-ref/`
  and contains a `SKILL.md`. If it lives elsewhere, ask the contributor
  and substitute that path everywhere below.

**Take a backup of the contributor's active skill before doing anything
else**, so a botched merge can't wipe their improvements:

    cp -a ~/.claude/skills/um-ref ~/.claude/skills/um-ref.pre-merge

Mention the backup to the contributor and tell them how to restore from it.

### Step 2 — Identify the BASE release

BASE is whichever upstream release the contributor originally installed
from. The **primary path** exploits the fact that most contributors
install by cloning/pulling this repo, then improve their active skill
(`~/.claude/skills/um-ref/`) while leaving the git clone alone. Under
that assumption, the local clone itself pinpoints BASE — no guessing.

Start with:

    git fetch origin
    git status
    git log HEAD..origin/main --oneline

Then work through the cases below in order.

**Case A — remote has commits ahead of HEAD** (contributor hasn't pulled
the latest release yet). This is the cleanest case.

- BASE = current HEAD.
- OURS = `origin/main`.
- Do **not** `git pull` before the merge. Extract both trees directly
  from refs — you don't need the working tree at OURS.

**Case B — local HEAD is at or ahead of `origin/main`** (contributor
already pulled, possibly just to get this very skill's install
instructions). Check the reflog for their previous HEAD:

    git reflog HEAD | head -20

Look for the most recent entry that advanced HEAD via `pull:` / `fetch:` /
`checkout:` / `reset:`. The commit *before* that move (its `HEAD@{N}`
predecessor) is the BASE candidate. Cross-check: `git show <candidate>:um-ref/SKILL.md`
against `~/.claude/skills/um-ref/SKILL.md` should show the maintainer's
changes since BASE but not the contributor's — sanity check that the
mismatch pattern makes sense.

- BASE = the pre-pull commit from reflog.
- OURS = current HEAD.

**Case C — no useful reflog** (fresh clone; expired reflog; contributor
doesn't remember). Fall back to enumerating candidates from tarball
history:

    git log --date=short --pretty='%h %ad %s' -- um-ref.tgz

Each commit that touched `um-ref.tgz` is a release candidate. Narrow
down by:

1. **Ask the contributor.** They may know the install date or version.
2. **Check `stat` on their SKILL.md** — the mtime is usually near their
   install date:

        stat -c '%y' ~/.claude/skills/um-ref/SKILL.md

   Match against commit dates from `git log`.
3. **Content-match.** For each candidate, extract into a scratch dir and
   count files that byte-match the contributor's tree. The candidate
   with the fewest differences is the most likely BASE.
4. **Prefer explicit tags.** If `git tag -l 'base-*'` returns anything,
   those are maintainer-marked release points — use them by name.

**Extract BASE into a scratch directory** (any case, once identified):

    BASE_DIR=$(mktemp -d)
    git show <base-commit-or-tag>:um-ref.tgz | tar xz -C "$BASE_DIR"
    ls "$BASE_DIR/um-ref/"

Verify the extracted tree looks right — contains `SKILL.md`, `lbmopt.py`,
and the deep-dive files that were shipped at that release. If BASE was
identified in Case A/B via the git clone, the extracted tarball tree
should be byte-identical to `git show <base-commit>:um-ref/` (the
expanded tree in the repo). A mismatch means the tarball and the
expanded tree drifted at that commit — flag it to the maintainer, but
prefer the tarball since that's what contributors actually installed.

**Note on the earliest releases:** some early commits shipped only the
tarball — no expanded `um-ref/` in the tree. For those, `git show <commit>:um-ref/`
will fail; you must extract from `um-ref.tgz` as shown above. All later
releases have both the tarball and the expanded tree.

### Step 3 — Build a synthetic 3-way merge repo

Git's merge machinery is 15+ years of edge-case handling — much better
than reinventing it with `diff3` or hand-merging. Set up a scratch git
repo where BASE, OURS, and THEIRS all share a common ancestor commit:

    MERGE_DIR=$(mktemp -d)
    cd "$MERGE_DIR"
    git init -q
    git config user.email "merge@localhost"
    git config user.name "um-ref merge"

    # BASE commit on default branch, tagged 'base' for clarity
    cp -a "$BASE_DIR"/um-ref/. .
    git add -A
    git commit -q -m base
    git tag base

    # THEIRS branch off BASE
    git checkout -q -b theirs
    find . -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
    cp -a ~/.claude/skills/um-ref/. .
    git add -A
    git commit -q -m theirs

    # OURS branch off BASE
    git checkout -q base -b ours
    find . -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
    cp -a "$REPO_ROOT/um-ref/". .
    git add -A
    git commit -q -m ours

    # Merge THEIRS into OURS
    git merge --no-commit --no-ff theirs || true

`$REPO_ROOT` is the absolute path to the upstream repo clone the
contributor is working in (typically the initial working directory
when this skill was invoked). Substitute the real path.

The merge either completes cleanly (rare) or leaves conflict markers.
Either way, don't commit yet — some files need policy overrides first.

### Step 4 — Apply policy overrides for generated / bundled files

Certain files in the skill are **not hand-authored** — they're either
generated from the UM source tree by `build.sh`, or bundled copies of
UM doc-source artifacts. They must always match the upstream release,
never a contributor's version:

| File                    | Origin                                       |
| ----------------------- | -------------------------------------------- |
| `java_api.md`           | Generated by `gen_java_api.py`               |
| `dotnet_api.md`         | Generated by `gen_dotnet_api.py`             |
| `config-data.xml`       | Bundled from UM `doc/Config/reference/`      |
| `index-ume.m4`          | Bundled from UM `doc/UME/`                   |
| `index-dro.m4`          | Bundled from UM `doc/DRO/`                   |

For each, take **OURS** unconditionally, regardless of merge state:

    git checkout --ours -- \
        java_api.md dotnet_api.md config-data.xml \
        index-ume.m4 index-dro.m4
    git add java_api.md dotnet_api.md config-data.xml \
        index-ume.m4 index-dro.m4

If any of these show up as edited on the contributor's side, flag it
to the contributor — that's almost certainly a mistake (either they
regenerated locally with a different UM source version, or they hand-
edited a bundled artifact). Do not silently accept those edits.

### Step 5 — Resolve remaining conflicts

Run `git status`. For each remaining unmerged file, read it, understand
both sides' intent, and attempt a **conservative semantic merge**. This
applies across the board — router tables, prose paragraphs, code blocks,
config examples, deep-dive sections — not just structured tables.

Git's line-level merge has already auto-resolved everything mechanically
resolvable; what remains is edits on overlapping lines that need judgement.
Classify each conflict block and act accordingly:

- **Additive, independent** — both sides added related but non-conflicting
  content in the same region (e.g. both appended a row to a table, both
  added a bullet to a list, both added a paragraph to the same section).
  **Merge textually** — keep both sides, in an order that reads well.
  Silent auto-resolve is fine here; no need to ask.
- **Additive, potentially redundant** — both sides added content that
  covers similar ground (e.g. both wrote a paragraph about the same
  concept from different angles). Attempt a merged paragraph that
  captures both intents; if you can't do so without loss, present the
  two options to the contributor and ask.
- **Contradictory** — both sides changed the same fact, rule, default
  value, code example, or claim, and the two versions can't both be
  true. **Stop and ask** the contributor which version should win, and
  why. Never silently pick one; never fabricate a compromise value.
- **Structural rewrite vs. small edit** — maintainer rewrote a section
  that the contributor made minor edits to. Ask whether the contributor's
  small edit still applies to the rewritten version, or whether their
  intent has been superseded.

Never silently drop either side's changes. Never fabricate content to
fill a conflict. When in doubt, ask — a contributor merge is
low-frequency, high-stakes, and worth a few clarifying questions.

Also handle these cross-tree cases (visible via `git status`):

- **Added by THEIRS only** — a new deep-dive file the contributor
  wrote. Keep it. Sanity-check that it's UM knowledge, not personal
  scratch (e.g., a `notes.md` about their own project should be
  excluded).
- **Added by OURS only** — new maintainer content the contributor
  didn't have. Keep it (nothing to reconcile).
- **Deleted by OURS, still in THEIRS** — the maintainer removed a
  file that the contributor may have edited. Confirm with the
  contributor: was the removed content moved elsewhere in OURS?
  Do they still need what they had? Do not silently restore.
- **Renamed** — git's rename detection usually handles this correctly.
  Verify by inspecting the merged file.

When everything is resolved:

    git add -A
    git commit -q -m merged

The tree in `$MERGE_DIR/` is now the authoritative merged skill.

### Step 6 — Apply the merged result in two places

**A) Update the contributor's active skill** so their live Claude sessions
pick up both maintainer improvements and their own edits:

    find ~/.claude/skills/um-ref -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
    cp -a "$MERGE_DIR"/. ~/.claude/skills/um-ref/
    rm -rf ~/.claude/skills/um-ref/.git

Tell the contributor their active skill is now updated, and the
pre-merge backup is at `~/.claude/skills/um-ref.pre-merge` if they
need to roll back.

**B) Stage the merged content on a branch in the upstream clone**,
ready for the contributor to open a PR:

    cd "$REPO_ROOT"
    git checkout -b merge-contribution-<short-description>
    find um-ref -mindepth 1 -maxdepth 1 -exec rm -rf {} +
    cp -a "$MERGE_DIR"/. um-ref/
    rm -rf um-ref/.git
    git status
    git diff --stat

Show the contributor the diff. **Stop before committing.** They should
review, then either instruct you to commit and prep a PR, or ask for
further adjustments.

If they approve, commit — but never `git push` without explicit
permission, since this is a public repo. `gh pr create` after push is
the contributor's decision.

### Step 7 — Leave the tarball alone

Do not update `um-ref.tgz` in the contributor's PR. The tarball is
re-packaged from `um-ref/` at release time by the maintainer as part
of `RELEASE_UPGRADE.md`'s workflow. Touching it in a contribution PR
creates a spurious binary diff that will conflict with the maintainer's
release process.

## Guardrails

- **Backup first.** Always `cp -a ~/.claude/skills/um-ref ~/.claude/skills/um-ref.pre-merge` before overwriting the contributor's active skill.
- **No pushes, no force-pushes, no branch deletions** without explicit contributor permission.
- **Preserve executable bits.** Use `cp -a` (archive mode), never `cp -r` — the skill's `.py` and `.sh` files are executable and the mode needs to survive.
- **Do not edit binary files by hand.** `um-ref.tgz`, `config-data.xml` (huge XML), and any images are opaque to a merge; take OURS.
- **Do not `git clean -fdx` or `git reset --hard` in the upstream repo clone.** Contributors may have local work you don't know about.

## When 3-way merge is overkill

If the contributor's improvements are trivial and independent of anything
the maintainer changed — e.g., a single new deep-dive file with no
`SKILL.md` edits — skip the merge machinery entirely. Copy the new
file(s) into `um-ref/`, verify OURS didn't add a colliding path, and
commit on a branch. The 3-way machinery is overhead when there's nothing
to reconcile.

Conversely, if the contributor rewrote the skill from scratch or made
architecturally sweeping changes, a mechanical merge won't capture the
intent — suggest they open a GitHub issue describing the changes first
so the maintainer can weigh in on approach before a big PR lands.

## Worked example

Contributor installed from an early tarball-only commit. They added a new
deep dive `wc_details.md` on wildcard receivers and inserted a router-table
entry for it in `SKILL.md`. Meanwhile, the maintainer has added
`configuration_best_practices.md` and rewritten `SKILL.md`'s §3 on Store
configuration.

BASE extraction (early commit shipped tarball only):

    BASE_DIR=$(mktemp -d)
    git show <early-commit>:um-ref.tgz | tar xz -C "$BASE_DIR"

Synthetic merge repo built per Step 3. Result of `git status` after
`git merge theirs`:

    both modified:   SKILL.md
    added by them:   wc_details.md
    added by us:     configuration_best_practices.md

Step 4 override: none of the auto-generated files are in conflict, no
overrides needed.

Step 5 resolution: `SKILL.md` conflict is in the router table — both
sides added a row in different regions of the same table. Resolve by
keeping both rows. `wc_details.md` and `configuration_best_practices.md`
are auto-added, no conflict.

Step 6: overlay merged tree onto `~/.claude/skills/um-ref/` and stage
on a branch `merge-contribution-wc-details` in the upstream clone.
Contributor reviews `git diff --stat`, approves, commits, opens PR.

## Notes for the `um-ref` skill maintainer (future improvements)

None of these are required for this skill to work, but they make future
contributor merges smoother:

- **Tag release commits.** After each release, `git tag base-<date>` on
  the commit that updates `um-ref.tgz`. Step 2 Case C will enumerate
  these tags automatically.
- **Consider dropping `get_skill.sh`.** With this contributor workflow,
  the source of truth for the skill is the repo's `um-ref/` directory,
  not the maintainer's `~/.claude/skills/um-ref/`. `get_skill.sh` copies
  in the wrong direction for that model. A replacement — call it
  `release.sh` — could just re-tar `um-ref/` for the release binary,
  and (optionally) rsync `um-ref/` → `~/.claude/skills/um-ref/` so the
  maintainer's active skill tracks the repo.
- **Ship a version marker.** Add a `VERSION` or `.installed-version`
  file to the skill so future Step 2 base-identification is trivial
  (`cat ~/.claude/skills/um-ref/VERSION`) instead of relying on
  mtime heuristics or content matching.
