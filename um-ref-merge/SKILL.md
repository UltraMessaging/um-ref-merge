# um-ref-merge — install, update, and contribute for the `um-ref` skill

## Scope

This skill covers three related workflows against the upstream `um-ref`
repo (https://github.com/UltraMessaging/um-ref):

- **Install** — copy the skill from a fresh repo clone into
  `~/.claude/skills/um-ref/`. No active skill exists yet.
- **Update** — pull newer skill content into an existing active skill,
  preserving whatever local edits the user (or Claude on their behalf)
  has made. Uses a 3-way merge anchored at the user's installed
  VERSION.
- **Contribute** — same 3-way merge as Update, plus stage the merged
  result on a branch in the repo clone for the user to open a pull
  request.

All three assume the user is running Claude inside a git clone of the
upstream `um-ref` repo. If the working directory isn't a clone, ask
them to clone it first.

If the user is the **um-ref maintainer** doing a UM version upgrade of
the skill, this is the wrong tool — direct them to
`um-ref/RELEASE_UPGRADE.md`. This skill handles user-facing flows, not
upstream releases.

## Choosing the workflow

Decide first, before running anything:

- `~/.claude/skills/um-ref/` **does not exist** → **Install**.
- `~/.claude/skills/um-ref/` exists, user asks to update / sync / pick
  up the latest → **Update**.
- User asks to contribute / merge changes back / open a PR →
  **Contribute**.

If intent is ambiguous, ask.

## Install workflow

Preconditions:

- Working directory is a clone of the upstream repo.
- `~/.claude/skills/um-ref/` does **not** exist. If it does, the user
  is Updating, not Installing.
- `$REPO_ROOT/um-ref/VERSION` exists (true for all releases 1.0+).

Steps:

    mkdir -p ~/.claude/skills
    cp -a "$REPO_ROOT/um-ref" ~/.claude/skills/

Confirm:

    cat ~/.claude/skills/um-ref/VERSION

Tell the user which VERSION they installed and that future updates
will use it as the 3-way-merge anchor.

That's the whole workflow. There is nothing on the user's side to
preserve, so no merge is needed.

## Update and Contribute — the 3-way merge

Update and Contribute share almost all their steps. They diverge only
in the final step: Contribute stages the merged content on a branch in
the repo clone for a PR; Update does not.

### Why a 3-way merge

Between the user's install and current upstream HEAD, both sides may
have been editing the skill:

- The **maintainer** committed new releases with improved content.
- The **user** improved their `~/.claude/skills/um-ref/` — often by
  asking Claude "do you have knowledge to add?" during earlier
  sessions.

Neither side has git history of the other's edits. Combining them
correctly requires a **3-way merge**:

| Role   | Content                                      | Location                            |
| ------ | -------------------------------------------- | ----------------------------------- |
| BASE   | The release the user originally installed    | `release-<VERSION>` tag in the repo |
| OURS   | Current upstream `um-ref/`                   | Repo clone (`origin/main`)          |
| THEIRS | The user's active skill                      | `~/.claude/skills/um-ref/`          |

Copying the repo over would lose the user's changes. A 2-way diff of
BASE vs. THEIRS cannot distinguish user edits from maintainer edits
that landed independently. Anchoring at BASE distinguishes them.

### Step 1 — Preconditions and backup

- Working directory is a clone of the upstream `um-ref` repo with a
  clean `git status`.
- `~/.claude/skills/um-ref/` exists and contains `SKILL.md`. If it
  lives elsewhere, ask the user and substitute that path throughout.

Take a backup of the active skill first — always:

    cp -a ~/.claude/skills/um-ref ~/.claude/skills/um-ref.pre-merge

Tell the user about the backup and how to restore from it.

Fetch:

    cd "$REPO_ROOT"
    git fetch origin --tags

### Step 2 — Identify BASE via VERSION

The active skill's `VERSION` file names the release the user is
currently on. That name maps directly to a `release-<VERSION>` tag in
the upstream repo:

    INSTALLED_VERSION=$(cat ~/.claude/skills/um-ref/VERSION)
    BASE_TAG="release-$INSTALLED_VERSION"
    git rev-parse --verify "$BASE_TAG" >/dev/null

If the tag doesn't exist, do not guess — stop and ask the user to
verify their VERSION content. A silent "approximate" fallback would
produce a subtly incorrect merge.

Extract BASE into a scratch directory (contents at top level, no
`um-ref/` prefix):

    BASE_DIR=$(mktemp -d)
    git archive "$BASE_TAG":um-ref | tar x -C "$BASE_DIR"
    ls "$BASE_DIR"

Sanity-check: the extracted tree should contain `SKILL.md`, `VERSION`,
and the deep-dive files that shipped at that release.
`cat $BASE_DIR/VERSION` should equal `$INSTALLED_VERSION`.

Determine OURS by reading upstream's VERSION:

    OURS_VERSION=$(git show origin/main:um-ref/VERSION | tr -d '[:space:]')

- If `OURS_VERSION == INSTALLED_VERSION`, there is no newer release.
  The user may still have local edits worth contributing (proceed if
  they asked to Contribute; skip the merge and report "already up to
  date" if they asked to Update).
- If `OURS_VERSION` is newer, note whether the bump is **major** (first
  digit changed — structural changes may invalidate local
  customizations; be extra careful in Step 5) or **minor** (usually
  merge-safe). Tell the user which.

Extract OURS into a scratch dir:

    OURS_DIR=$(mktemp -d)
    git archive origin/main:um-ref | tar x -C "$OURS_DIR"

### Step 2 (fallback) — pre-1.0 installs (no VERSION file)

If the active skill has no `VERSION` file, the user installed under
the old wget-tarball scheme (before release 1.0). BASE is buried in
git history — recover it by content matching:

1. Enumerate commits that touched `um-ref.tgz` (historical only —
   1.0+ releases do not include it):

        git log --date=short --pretty='%h %ad %s' -- um-ref.tgz

2. For each candidate, extract into a scratch dir:

        mkdir -p /tmp/candidates
        git show <commit>:um-ref.tgz | tar xz -C /tmp/candidates/<hash>
        # Contents live at /tmp/candidates/<hash>/um-ref/*

3. `diff -r` each candidate's `um-ref/` against
   `~/.claude/skills/um-ref/`. The candidate with the fewest
   differences is the most likely BASE.
4. Cross-check with the user — install date? UM version they
   remember?
5. Ask before proceeding. Getting BASE wrong on a pre-1.0 install
   produces a subtly incorrect merge; do not silently pick.

Once identified, extract the tarball's `um-ref/` contents into
`$BASE_DIR` (flatten so the layout matches the VERSION-based path):

    BASE_DIR=$(mktemp -d)
    git show <base-commit>:um-ref.tgz | tar xz --strip-components=1 -C "$BASE_DIR"

Then continue with Step 3.

### Step 3 — Build a synthetic 3-way merge repo

Git's merge machinery is 15+ years of edge-case handling — much
better than reinventing it with `diff3` or hand-merging. Set up a
scratch git repo where BASE, OURS, and THEIRS all share a common
ancestor commit:

    MERGE_DIR=$(mktemp -d)
    cd "$MERGE_DIR"
    git init -q
    git config user.email "merge@localhost"
    git config user.name "um-ref merge"

    # BASE commit on default branch, tagged 'base' for clarity
    cp -a "$BASE_DIR"/. .
    git add -A
    git commit -q -m base
    git tag base

    # THEIRS branch off BASE
    git checkout -q -b theirs
    find . -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
    cp -a ~/.claude/skills/um-ref/. .
    git add -A
    git commit -q -m theirs

    # OURS branch off BASE
    git checkout -q base -b ours
    find . -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
    cp -a "$OURS_DIR"/. .
    git add -A
    git commit -q -m ours

    # Merge THEIRS into OURS
    git merge --no-commit --no-ff theirs || true

The merge either completes cleanly (rare) or leaves conflict markers.
Either way, don't commit yet — some files need policy overrides
first.

### Step 4 — Apply policy overrides for generated / bundled files

Certain files in the skill are **not hand-authored** — they're either
generated from the UM source tree by `build.sh`, or bundled copies of
UM doc-source artifacts. They must always match the upstream release,
never a user's version. `VERSION` itself is likewise not hand-authored
— it's set by the maintainer at release time.

| File               | Origin                                       |
| ------------------ | -------------------------------------------- |
| `VERSION`          | Set by maintainer at release                 |
| `java_api.md`      | Generated by `gen_java_api.py`               |
| `dotnet_api.md`    | Generated by `gen_dotnet_api.py`             |
| `config-data.xml`  | Bundled from UM `doc/Config/reference/`      |
| `index-ume.m4`     | Bundled from UM `doc/UME/`                   |
| `index-dro.m4`     | Bundled from UM `doc/DRO/`                   |

For each, take **OURS** unconditionally, regardless of merge state:

    git checkout --ours -- \
        VERSION java_api.md dotnet_api.md config-data.xml \
        index-ume.m4 index-dro.m4
    git add VERSION java_api.md dotnet_api.md config-data.xml \
        index-ume.m4 index-dro.m4

If any of these show up as edited on the user's side, flag it — that's
almost certainly a mistake (they regenerated locally with a different
UM source version, hand-edited a bundled artifact, or manually touched
VERSION). Do not silently accept those edits.

### Step 5 — Resolve remaining conflicts

Run `git status`. For each remaining unmerged file, read it,
understand both sides' intent, and attempt a **conservative semantic
merge**. This applies across the board — router tables, prose
paragraphs, code blocks, config examples, deep-dive sections — not
just structured tables.

Git's line-level merge has already auto-resolved everything
mechanically resolvable; what remains is edits on overlapping lines
that need judgement. Classify each conflict block and act accordingly:

- **Additive, independent** — both sides added related but
  non-conflicting content in the same region (e.g. both appended a
  row to a table, both added a bullet to a list, both added a
  paragraph to the same section). **Merge textually** — keep both
  sides, in an order that reads well. Silent auto-resolve is fine
  here; no need to ask.
- **Additive, potentially redundant** — both sides added content
  that covers similar ground (e.g. both wrote a paragraph about the
  same concept from different angles). Attempt a merged paragraph
  that captures both intents; if you can't do so without loss,
  present the two options to the user and ask.
- **Contradictory** — both sides changed the same fact, rule,
  default value, code example, or claim, and the two versions can't
  both be true. **Stop and ask** the user which version should win,
  and why. Never silently pick one; never fabricate a compromise
  value.
- **Structural rewrite vs. small edit** — maintainer rewrote a
  section that the user made minor edits to. Ask whether the user's
  small edit still applies to the rewritten version, or whether
  their intent has been superseded. A **major** VERSION bump (per
  Step 2) is a strong hint this case will show up.

Never silently drop either side's changes. Never fabricate content
to fill a conflict. When in doubt, ask.

Also handle these cross-tree cases (visible via `git status`):

- **Added by THEIRS only** — a new deep-dive file the user wrote.
  Keep it. Sanity-check that it's UM knowledge, not personal
  scratch (e.g., a `notes.md` about their own project should be
  excluded from a contribution PR).
- **Added by OURS only** — new maintainer content the user didn't
  have. Keep it (nothing to reconcile).
- **Deleted by OURS, still in THEIRS** — the maintainer removed a
  file that the user may have edited. Confirm with the user: was
  the removed content moved elsewhere in OURS? Do they still need
  what they had? Do not silently restore.
- **Renamed** — git's rename detection usually handles this
  correctly. Verify by inspecting the merged file.

When everything is resolved:

    git add -A
    git commit -q -m merged

The tree in `$MERGE_DIR/` is now the authoritative merged skill.

### Step 6 — Apply the merged result

Both Update and Contribute update the user's active skill so their
live Claude sessions pick up the merge:

    find ~/.claude/skills/um-ref -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
    cp -a "$MERGE_DIR"/. ~/.claude/skills/um-ref/
    rm -rf ~/.claude/skills/um-ref/.git

Tell the user their active skill is now updated, that VERSION is now
`$OURS_VERSION`, and that the pre-merge backup remains at
`~/.claude/skills/um-ref.pre-merge` if they need to roll back.

**For Update, stop here.** The workflow is complete.

**For Contribute**, additionally stage the merged content on a
branch in the upstream clone, ready for a pull request:

    cd "$REPO_ROOT"
    git checkout -b merge-contribution-<short-description>
    find um-ref -mindepth 1 -maxdepth 1 -exec rm -rf {} +
    cp -a "$MERGE_DIR"/. um-ref/
    rm -rf um-ref/.git
    git status
    git diff --stat

Show the user the diff. **Stop before committing.** They should
review, then either instruct you to commit and open a PR, or ask for
further adjustments.

Even after review approval, do not `git push` without explicit
permission — this is a public repo. `gh pr create` after push is the
user's decision.

## Guardrails

- **Backup first.** Always
  `cp -a ~/.claude/skills/um-ref ~/.claude/skills/um-ref.pre-merge`
  before overwriting the user's active skill.
- **No pushes, no force-pushes, no branch deletions** without
  explicit user permission.
- **Preserve executable bits.** Use `cp -a` (archive mode), never
  `cp -r` — the skill's `.py` and `.sh` files are executable and
  the mode needs to survive.
- **Do not edit binary files by hand.** `config-data.xml` (huge
  XML) and any images are opaque to a merge; take OURS.
- **Do not `git clean -fdx` or `git reset --hard` in the upstream
  repo clone.** Users may have local work you don't know about.
- **VERSION is not the user's to edit.** It's a machine-managed
  anchor. Take OURS unconditionally.

## When 3-way merge is overkill

If the user's improvements are trivial and independent of anything
the maintainer changed — e.g., a single new deep-dive file with no
`SKILL.md` edits — skip the merge machinery entirely for Contribute.
Copy the new file(s) into `um-ref/`, verify OURS didn't add a
colliding path, and commit on a branch. The 3-way machinery is
overhead when there's nothing to reconcile.

Conversely, if the user rewrote the skill from scratch or made
architecturally sweeping changes, a mechanical merge won't capture
the intent — suggest they open a GitHub issue describing the changes
first so the maintainer can weigh in on approach before a big PR
lands.

## Worked example

User's active skill has `VERSION` file with content `1.0`. Upstream
has released `1.2` (a minor bump). The user added a new deep dive
`wc_details.md` on wildcard receivers and inserted a router-table
entry for it in `SKILL.md`. Meanwhile, between 1.0 and 1.2, the
maintainer added `configuration_best_practices.md` and rewrote
`SKILL.md`'s §3 on Store configuration.

BASE lookup:

    INSTALLED_VERSION=$(cat ~/.claude/skills/um-ref/VERSION)   # → 1.0
    BASE_TAG="release-1.0"
    BASE_DIR=$(mktemp -d)
    git archive "$BASE_TAG":um-ref | tar x -C "$BASE_DIR"

OURS = `origin/main:um-ref` at `VERSION=1.2`. Extract to `$OURS_DIR`.

Synthetic merge repo built per Step 3. Result of `git status` after
`git merge theirs`:

    both modified:   SKILL.md
    both modified:   VERSION
    added by them:   wc_details.md
    added by us:     configuration_best_practices.md

Step 4 overrides: `VERSION` is on the policy-override list — take
OURS (`1.2`). No conflicts in the other generated files.

Step 5 resolution: `SKILL.md` conflict is in the router table —
both sides added a row in different regions of the same table.
Resolve by keeping both rows. `wc_details.md` and
`configuration_best_practices.md` are auto-added, no conflict.

Step 6: overlay merged tree onto `~/.claude/skills/um-ref/`; if the
user is Contributing, stage a branch `merge-contribution-wc-details`
in the upstream clone. User reviews `git diff --stat`, approves,
commits, opens PR.
